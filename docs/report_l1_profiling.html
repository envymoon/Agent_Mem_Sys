Agent 记忆系统 L4 剖析

在一张 L4 上同时跑对话 agent、记忆系统和本地 LLM，逐环节记录每一轮的时间和资源都花在哪里。比较对象是 mem0 的三种存储后端和一个纯检索的 RAG 基线。写入路径全部改为异步，并保留此前的同步数据做对照。LoCoMo 和 LongMemEval-S 只用来提供真实负载，分数仅作参考。

结论

77%LoCoMo 上 mem0 每轮 LLM 忙碌时间中，记忆写入所占比例（4.37 s 对 agent 的 1.30 s）
97%mem0 add 耗时中那一次 LLM 抽取调用的占比；其余 9 个阶段合计约 135 ms
75%抽取调用的 decode 时间中，用于 reasoning token 的比例（188 个推理 token 对 64 个 JSON token）
85%decode 主力 kernel（MXFP4 MoE matvec）达到的 DRAM 带宽峰值比例：decode 受带宽限制
  1. 瓶颈在记忆写入，不在检索。mem0 每轮在后台花 4.5–4.8 s 写记忆，而用户等待的前台只有 1.38 s。在 nsys 抓取的约 19 s 窗口里（第 10–12 轮），mem0 的 GPU kernel 时间是 11.6–16.3 s，rag-pg 只有 3.0 s，约为 4–5 倍。
  2. mem0 add 实质上就是一次 LLM 调用。抽取调用占 add 的 97%。它的 prompt 约 8.5k token，但前缀缓存命中 91%，所以 prefill 加排队只要 0.33 s；时间主要花在 decode 上，3.9 s 中有 2.9 s 是 gpt-oss 的 reasoning。embedding、NER、数据库读写等 9 个阶段合计约 135 ms。
  3. decode 受显存带宽限制，prefill 两头都没吃满。Nsight Compute 显示：decode 时 MXFP4 MoE matvec 达到 DRAM 峰值的 85%，Q8_0 dense matvec 达到 68%，tensor core 完全空闲。输出头（Q8_0，约 20 万词表）每个 token 要 2.4 ms，约占全部 kernel 时间的 14%。prefill 的 mmq kernel 只用到 SM 55%、tensor 28%、DRAM 26%，每个 SM 的活跃 warp 被限制在 16.7%。
  4. 记忆抽取的 decode 阶段 GPU 有四成时间在空转。记忆 reasoning 段 GPU 忙碌率只有 48–58%，而 agent 的单流 decode 是 84–87%。llama-server 进程稳定占满约一个 CPU 核（89–103%）。推测每个 token 的 CPU 路径是瓶颈：mem0 用 response_format 要求 JSON，需要逐 token 做语法约束采样；另外抓 trace 时关闭了 CUDA graph，kernel 启动开销也被放大。这一条是推断，尚未单独验证。
  5. 异步写入大幅缩短用户等待，但有两个代价。用户每轮等待时间：LoCoMo 从 5.6–6.0 s 降到 1.38 s；LongMemEval 从 9.4–10.3 s 降到 3.5–3.8 s。代价一是争抢 GPU，agent 每个 token 的 decode 时间从 12.2 ms 涨到 14.4 ms（LoCoMo），LongMemEval 上从 12.7 ms 涨到 18.5 ms。代价二是记忆变得不新鲜：提交延迟中位数在 LoCoMo 上是 4.1–4.8 s，在 LongMemEval 上是 17–34 s，最长 188 s，队列最多积压 17 条。原因是 LongMemEval 上一次 add 要 7.8–8.5 s，几乎等于两轮之间的间隔（约 3.5 s 回答加 5 s 思考）。
  6. 只有 mem0-local 随存储增长明显变慢。在 240 轮的会话里，mem0-local 的检索从 176 ms 涨到 430 ms；它的向量库是进程内的嵌入式 Qdrant，压测进程占 71% CPU，常驻内存 2.25 GB。mem0-pg 和 mem0-qdrant 基本持平，在 115–160 ms 之间；rag-pg 一直是 13–17 ms。add 里的实体查找也是同样规律：mem0-local 447 ms，mem0-pg 165 ms，mem0-qdrant 43 ms。
  7. mem0 把读时的 prefill 换成了写时的 decode。rag-pg 写入不调 LLM，只要 23–41 ms，提交延迟低于 0.4 s；代价是回答 prompt 有 4.8k token（mem0 是 1.1k），LongMemEval 上 prefill 要 1.67 s（mem0 是 0.56 s）。最终用户等待时间相近，rag-pg 4.2 s，异步 mem0 3.5–3.8 s，但 mem0 消耗的 GPU 时间多出数倍。

实验设置与测量方法

这一节按“一次运行从启动到出数”的顺序，说明每个环节做了什么、在哪里打的点、数字怎么算出来。原则是不改被测系统的源码：mem0 和 RAG 基线都按原样运行，测量全部靠外部包装（monkeypatch）、一个夹在中间的 LLM 代理和独立的采样进程完成。

1. 一次运行怎么跑起来

  1. 调度。用 colab CLI 开一台 L4 运行时。虚拟机上的 colab/supervisor.py 按 colab/queue.txt 依次执行套件（l1、lme、kprof、score），每个套件调用一次 scripts/local/run_local_suite.sh。失败会自动重试。每个跑完的运行目录打包放进 outbox，由我用 colab download 取回，再提交到仓库。
  2. 启动推理栈（start_llama.sh）。先起 embedding 服务（:8001），再起 LLM 服务（:8000），最后起 memprof 代理（:8100）。实际命令行和每块显存的分配都记进 llm.cmd 和 llm.load.json，防止显存不够时 llama.cpp 悄悄回退、改变了实验条件。
  3. 每个运行之前先清场。
    • 停掉 Postgres 和 Qdrant，删除它们的数据目录再重建，所以每次运行都从空库开始。
    • 运行目录整个删掉重建，mem0-local 的嵌入式 Qdrant 和 SQLite 就在这个目录里。
    • 清页缓存。容器里 drop_caches 不可写，改用 posix_fadvise(DONTNEED) 按文件逐出。但 Colab 的数据目录在 overlay 文件系统上，preflight 没能从块设备计数确认逐出生效（记到的冷读设备字节为 0），所以本报告不对冷、热页缓存做结论。
  4. 开始采集。启动硬件采样进程 memprof.hwmon，并通知代理把日志切换到本次运行的 llm_calls.jsonl。
  5. 运行 bench/multi_e2e.py，依次执行：
    • 冷启动 cold.start：建表、建集合、加载 spaCy。
    • 逐轮回放对话。
    • 异步模式下等后台队列排空。
    • 问答。
    • 统计存储大小，写出 spans.jsonl、meta.json 和 qa.json。
  6. 后处理。
    • analysis/multi_breakdown.py 生成 breakdown_multi.json。
    • kprof 运行再由 analysis/kernel_profile.py 生成 kernel_profile.json。
    • score 套件由 analysis/qa_score.py 打分。
    • analysis/report_l1_data.py 把以上结果汇总成本报告用的数据。

5. 每类数据是怎么抓的

5.1 span 计时器memprof/tracer.py

  • 用 with TRACER.span(name) 包住一段代码，进入和退出时各取一次：
    • 墙钟：perf_counter_ns。
    • CPU 时间：process_time_ns，本进程所有线程合计，ONNX 和 numpy 的工作线程也算在内。
    • /proc/self/io 计数：rchar/wchar 是经过 read/write 系统调用的字节；read_bytes/write_bytes 是真正落到块设备的字节。
    • 缺页次数：getrusage。
  • 每个线程维护自己的嵌套栈，记录父 span，并附上当前阶段（chat、qa、cold）和轮号。
  • 不改源码，全部用 monkeypatch 包装：
    • mem0 内部：Memory.add、Memory.search、_compute_entity_boosts、score_and_rank。
    • spaCy：词形还原（BM25 用）和 NER；BM25 编码。
    • 存储与 embedding 客户端：SQLite 历史库、embedding 客户端。
    • 数据库驱动：psycopg 的 execute、executemany、commit；QdrantClient 的各个读写方法。mem0-local 的嵌入式 Qdrant 用的也是这个类，所以三种后端测法一致。
  • 可能并发的调用（数据库驱动、后台线程里的调用）记成“扁平区间”，不进嵌套栈；分析时按区间并集处理，不会重复计数。
  • 开销：每次运行开头实测一个空 span 的开销，约 44–46 µs，存进 meta.json。一轮几十个 span，合计不到几毫秒。

5.2 LLM 代理memprof/llm_proxy.py

  • agent 和所有被测系统的 base_url 都指向代理。代理把请求中的模型名改成本地模型，再转发给 llama-server。
  • 非流式请求改成流式。mem0 发的是普通的非流式请求，拿不到首 token 时间。代理把它改成流式发给 llama-server，收完再拼成非流式响应返回。被测系统完全感知不到，但每次调用都能测到首 token。
  • reasoning 和 answer 分开计数。逐个解析流式 chunk：
    • 带 reasoning_content 的计为 reasoning token。
    • 带 content 或 tool_calls 的计为 answer token。llama.cpp 每个 chunk 恰好一个 token。
    • 记下首 token 时刻和首个 answer token 时刻，decode 就以后者为界拆成 reasoning 段和 answer 段。
  • 服务端计时。从最后一个 chunk 的 usage 和 llama.cpp 的 timings 中取 prompt token 数和生成 token 数，以及：
    • cache_n：命中前缀缓存、不用重算的 token 数。
    • prompt_ms：服务端实际做 prefill 的时间。
  • 排队时间估计。首 token 时间 − prompt_ms − 2 ms，其中 2 ms 是 HTTP 和首个 chunk 的固定开销。这个数是上界：两路请求合批时，prefill 本身也会被另一路拖慢。
  • 区分调用来源。agent 的请求带请求头 X-Memprof-Client: agent，其余都算记忆系统自己的调用。
  • embedding 请求同样经过代理，记录起止时间和输入条数。

5.3 时间归因：每轮分解的几段是怎么来的analysis/multi_breakdown.py

  • 一个操作区间（比如一次 add）里会有多个子区间：LLM 调用、embedding、数据库、spaCy。它们可能互相重叠，例如并发的数据库调用。
  • 用扫描线把区间里的每一时刻只归给一个类别，按下面的优先级取最高者：
    1. LLM decode（reasoning 段和 answer 段同级）
    2. LLM prefill + 排队
    3. Embedding
    4. DB
    5. NLP
    6. 其他：没有被任何子区间覆盖的时间，即 Python 胶水代码、序列化、HTTP 开销
    各类加起来正好等于操作的墙钟时间。
  • agent.generate 只统计 agent 标签的调用，写入操作只统计记忆系统的调用，所以异步模式下前台和后台的 LLM 时间不会混在一起。
  • 报告中前台条的“非 LLM 与调用开销” = agent.turn 的墙钟 − agent.generate 的三段 LLM 时间。
  • 每个操作都取第 1 轮起的均值，同时给出 p50、p95 和最大值。

5.4 mem0 add 的 10 个阶段bench/systems/mem0_sys.py

  • 打点方法。mem0 2.2.1 的写入流水线 _add_to_vector_store 是一个顺序执行的大函数，无法单独包住每个阶段。做法是在每个阶段第一个调用的函数上打时间标记：一个阶段从自己的标记开始，持续到下一个阶段的标记，阶段之间的 Python 代码也算进去。
  • 标记只能往后走，阶段号必须递增。这样一个阶段内部重复调用某个函数，不会被错误地切回前一个阶段。
  • 跳过的阶段（没抽出新记忆时，后 7 段都不执行）按 0 计入均值。
  • 阶段内再拆分。每个阶段内部再按 5.3 的方法分成 LLM、embedding、DB、NLP 和其他。

5.5 同步与异步的指标定义

  • 用户等待：agent.turn 的墙钟，即检索、拼 prompt 和 agent 生成之和；同步模式下还包括写入，因为下一句要等写入完成才会被处理。不含思考时间。
  • 提交延迟：从后台任务提交，到这次 add 返回，包括在队列里等待的时间。add 返回后，这句话的记忆就可以被检索到。
  • 积压：每次提交时，队列里尚未完成的 add 数，包括刚提交的这一个。
  • agent 每 token 的 decode 时间：agent.generate 的 decode 时间 ÷ 它生成的 token 数（reasoning 加 answer）。
  • 后台只有一个写入线程，所以 add 串行执行。

5.6 硬件与进程采样memprof/hwmon.py

  • 每 0.25 s，GPU（NVML）：GPU 利用率、显存带宽利用率、显存占用、功耗、SM 频率、PCIe 吞吐。NVML 的利用率是“采样周期内有 kernel 在运行的时间比例”，只说明有没有 kernel 在跑，不说明 SM 用了多少，所以 kernel 级的忙碌率另用 nsys 测（5.8）。
  • 每 0.25 s，进程：用 psutil 按命令行把进程分组（llm_server、embed_server、postgres、qdrant、proxy、harness），记录每组的 CPU%（100% 等于一个核）和常驻内存。正文中“llama-server 占约一个核（89–103%）”和“mem0-local 压测进程 71% CPU、2.25 GB”都来自这里。
  • 每 1 s，llama.cpp /metrics：prompt token 总数、命中缓存的 token 总数、生成 token 总数和耗时。用首末两次的差值，算整次运行的前缀缓存命中率和平均吞吐。
  • 每 1 s，磁盘：各进程组的 /proc/<pid>/io、数据盘的 /proc/diskstats（含 flush 次数和耗时），以及 IO 压力（PSI）。

5.7 存储 I/O 与数据库

  • 同步模式下，每个操作前后各取一次快照，差值记到这个操作上：
    • 系统侧：各进程组的块设备读写字节和系统调用读写字节、磁盘 flush 次数。
    • Postgres 侧：pg_stat_statements（语句数、执行时间、共享缓冲命中与读盘、WAL 字节）、pg_stat_wal、pg_stat_io。
  • 异步模式下后台写入和前台并发，差值没法归到单个操作，只保留整次运行的总量。
  • 数据库配置。Postgres 保持默认的持久化设置（fsync 和 synchronous_commit 都开启），shared_buffers 2 GB，开启 IO 计时。
  • 磁盘基线（preflight 中用 fio 测得）：顺序读 4.8 GB/s；4k 随机读 5.9 万 IOPS；4k 写加 fsync 412 IOPS，平均每次 2.4 ms。
  • Colab 的数据目录在 overlay 文件系统上，块设备层的计数不一定能对应到具体文件。
  • 这次实验只有几千条记忆、几十 MB 数据，存储读写和 fsync 每轮都在毫秒级，所以正文没有展开。

5.8 GPU kernel 抓取（Nsight Systems）analysis/kernel_profile.py

  • 启动方式。kprof 套件让 llama-server 在 nsys launch --trace=cuda 的会话里启动，只跟踪 CUDA，不做 CPU 采样，启动后先不采集。这台机器上的 nsys 不支持 --cuda-graph-trace，为了看到 CUDA graph 里的每个 kernel，llama-server 以 GGML_CUDA_DISABLE_GRAPHS=1 运行。
  • 抓取窗口。每个系统单独跑一次 16 轮的异步 LoCoMo，同样有 5 s 思考时间：
    • 前 10 轮用来预热，让前缀缓存和存储进入稳态。
    • 第 10 轮开始前执行 nsys start，第 13 轮开始前执行 nsys stop。
    • 窗口约 19 s，覆盖第 10–12 轮的前台回答、第 9 轮写入的尾部，以及第 10–12 轮的完整写入。
  • 导出。把抓取结果导出成 SQLite，读出每个 kernel 的起止时间和完整名字，以及每次显存拷贝。
  • 分类。按 llama.cpp 的 kernel 名用正则分类，模板参数里带着量化类型：MXFP4 MoE matmul、Q8_0 dense matmul、flash attention、激活量化、norm、rope、softmax/top-k、KV 写入、逐元素运算等。
  • 对齐。nsys 和代理的时钟基准不同。把 kernel 活动和代理记录的 LLM 活动都切成 1 ms 的格子，用 FFT 互相关找到让两者重叠最多的平移量。校验：对齐后 98.5–99.9% 的 kernel 时间落在某次 LLM 调用之内。
  • 归因到阶段。
    • 用代理日志把每次 LLM 调用切成排队、prefill、reasoning、answer 四段，并标明是 agent 还是记忆系统的调用。prefill 段取首 token 之前、长度为 prompt_ms 的那一段。
    • 每个 kernel 按它的中点落在哪一段打标签。两路请求同时在跑时，标签是组合，例如 agent:answer+memory:reasoning，因为 llama.cpp 把两路请求合进同一次前向计算。
  • GPU 忙碌率 = 该段内 kernel 时间之和 ÷ 该段的墙钟时间。它能看到 kernel 之间的空隙，比 NVML 利用率精确。
  • embedding 服务是另一个进程，没有被跟踪。

5.9 硬件计数器（Nsight Compute）与吞吐基准

5.10 评分与规模分析analysis/qa_score.py

  • token F1：SQuAD 风格，去掉标点和冠词后，按词计算预测与标准答案的重合，即 LoCoMo 论文的指标。
  • LLM 评委：用同一个本地 gpt-oss-20b（经代理）判 CORRECT 或 WRONG。按题型使用不同规则，参照 LongMemEval 的评测脚本和 mem0 的 J 指标，例如时间题允许差一天，知识更新题要求给出最新值。论文用的评委是 GPT-4o，所以绝对值不能与论文直接对比。
  • 规模增长：把每个 LongMemEval haystack 按轮号均分成 5 段，越往后存储里的记忆越多。每段内对检索墙钟取均值，再对 3 个 haystack 取平均。

怎么读这张表

争抢。后台写入和前台回答共用一张卡，llama.cpp 以 -np 2 把两路 decode 合批。合批让 GPU 总吞吐更高（重叠段 GPU 忙碌率 85–90%），但单路变慢。rag-pg 没有后台 LLM 调用，所以异步前后完全一致。LoCoMo 上每轮写入约 4.5 s，大致能在 5 s 思考时间里做完，agent 每个 token 的 decode 只慢约 17%。LongMemEval 上每次写入 7.8–8.5 s，前台回答时几乎总有一路写入在跑，每个 token 慢约 45%。

新鲜度。提交延迟是从用户说完一句话，到这句话的记忆可以被检索到的时间。LoCoMo 上它约等于一次 add 的耗时，说明队列基本不积压。LongMemEval 上写入速度略低于对话速度，队列会积压，中位数 17–34 s，最长 188 s。也就是说，用户几轮之前说的话可能还没进入记忆。思考时间越短（真实打字越快），这个问题越严重。

GPU 利用率。在 LongMemEval 上，异步加思考时间后，rag-pg 的平均 GPU 利用率从 90% 掉到约 42%，因为思考时间里没有工作。mem0 仍保持在 84–86%，因为后台写入填满了这些空闲时间。

注意事项

CUDA graph。nsys 2025.3 不支持 --cuda-graph-trace，为了看到单个 kernel，kernel 抓取时 llama-server 以 GGML_CUDA_DISABLE_GRAPHS=1 运行。这会增加 kernel 启动开销，使 kernel 抓取中的 GPU 忙碌率偏低，尤其是单路 decode。各类 kernel 的占比和 ncu 计数器不受影响。
类别名。VM 上分析 kernel 时用的是旧分类名 “matmul (quantized, other)”，在 gpt-oss-20b 上它对应 Q8_0 dense matmul（注意力投影和输出头）。本报告统一写作 “Q8_0 dense”。
对照条件。同步对照组没有思考时间，异步组有 5 s，所以两组的平均 GPU 利用率不能直接比较。同步运行是 reasoning 拆分功能上线前做的，没有 reasoning / answer 分段，表中只比较了总 decode 和每 token 时间。
样本。kernel 抓取覆盖第 10–12 轮的前台回答及其后台写入（约 19 s）。ncu 数据来自 llama-bench，而不是真实请求。LongMemEval 只有 3 个 haystack。所有实验各跑一次，没有重复。
